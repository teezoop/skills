# Bug 诊断

仅在用户显式调用 `diagnosing-bugs` 时执行，例如 `$diagnosing-bugs` 或 `/diagnosing-bugs`。本技能的交付物是 **bug 诊断结论**，包括根因、修复方案，以及所有已测试假设及其结果。本技能不主动实施最终bug修复，需要用户决定是否最终按照交付的修复方案实施。

## 工作边界

- 本技能只排查原因、验证假设并提出方案，不实施最终修复。
- 用户最终确认修复方案前，禁止直接编写或保留最终修复代码；临时诊断改动按下文的实验规则处理。
- 禁止通过临时修复或绕过问题来掩盖 bug，除非用户明确允许这样做。
- 用户最终确认方案并要求实施后，结束诊断流程，另行进入修复任务；展示假设、验证假设或提交诊断结论，都不等于获得实施修复的授权。

## 1. 先阅读相关代码

根据错误报告、错误描述、复现条件、调用栈和日志定位相关模块。排查过程中务必先查看代码，熟悉模块实现细节，再作原因判断。

至少理解相关入口、调用关系、关键状态或数据的流转，以及异常发生的路径。将报告中的现象和栈帧对应到实际实现，不能只凭错误文案、模块名称或表面症状推断原因。

## 2. 有条件时先尝试复现

在了解相关代码和执行路径后，已有复现条件时，先按这些条件尝试复现，再基于结果深入排查。记录输入、操作步骤、环境或版本、实际现象与预期行为。

确认复现的是用户报告的同一个问题，而不是附近的另一种失败。保留可核对的错误、日志、调用栈或输出。

复现失败或缺少条件时，如实记录已尝试的步骤、结果与缺失条件，并基于现有代码和证据继续排查；无法复现不代表 bug 不存在。

## 3. 追踪根因

沿错误报告、错误描述、调用栈、日志及相关代码追踪问题的因果链，找出错误状态或错误数据最初如何产生，以及它如何传递到用户看到的症状。

最终应能解释：**触发条件 → 具体实现中的缺陷或失效假设 → 错误传播路径 → 表面症状**。指明相关代码位置和支持该因果关系的证据，不把最后抛错的位置、空值、超时或其他表面现象直接当成根因。

必要时查询相关路径的近期提交，例如使用 `git log`、`git show` 或 `git blame`，核对问题是否由最近的行为、接口、状态或配置变更引入。不要仅因某次提交较新，就认定它是原因。

## 4. 需要测试时，先列出可证伪假设

需要通过测试区分可能原因时，先生成**按优先级排序的 3 至 5 个假设**，不要只提出一个看似合理的解释。按现有证据、与症状的吻合程度和验证价值排序。

每个假设都应包含：

- **原因**：具体怀疑什么，以及已有证据为何支持怀疑它。
- **可证伪预测**：如果该原因成立，什么观察或受控变化应让症状消失、减轻或恶化；什么结果会与该假设矛盾。
- **验证方法**：如何观察或测试该预测，以及怎样区分它与其他解释。

预测可采用以下形式：

> 如果 X 是原因，那么改变 Y 会让缺陷消失，或改变 Z 会让缺陷更严重；如果实际结果与预测矛盾，则该假设不成立。

无法给出预测的假设只是感觉，丢弃它或进一步明确。

**测试前，先向用户展示排序后的假设清单。** 根据用户反馈调整；用户不在时，按已展示的排序继续。每轮只测试一个假设，结合新证据更新结论和后续排序。

### 临时实验与回退

测试假设可以采用观察、日志、断点、诊断脚本、测试或最小临时代码及环境改动。临时改动只服务于验证，不得借此提前实施整套最终修复方案。

每轮实验都应：

1. 记录实验前相关代码和环境的基线，包括已有的未提交改动，以及本轮准备临时改变的内容。
2. 只验证当前假设，控制变量，记录操作、预测和实际结果。结果分为“支持”“排除”或“仍不确定”，不能把测试运行成功直接等同于假设成立。
3. 测试结束后回退本轮对代码或环境的临时修改，包括临时插桩、测试文件和配置。无论假设是否成立、测试失败或中止，都要执行回退。
4. 核对相关状态已恢复到实验前基线。只撤销本轮诊断改动，保留用户原有修改。回退受阻时先说明并处理残留，恢复完成后再开始下一轮。

回退临时改动的同时，保留实验观察和证据，供最终报告引用。

## 5. 输出 bug 诊断结论

最终报告必须包含以下内容。

### 根因

说明复现情况、根因所在的模块和代码位置、触发条件、错误传播过程，以及支持结论的代码、日志、调用栈或实验依据。

区分已确认事实与推断。如果证据不足以确认根因，明确写“根因尚未确认”，列出当前最可能的原因和缺失证据，不将猜测包装成根因。

### 修复方案

可以给出一个或多个方案；有多个时，按推荐优先级从高到低排列。每个方案都说明：

- **准备改哪里**：涉及的模块、函数、接口、状态或配置。
- **准备怎么改**：计划改变的行为或逻辑。
- **为什么这样改**：如何消除根因，为什么推荐，其他方案有哪些取舍。
- **如何验证**：计划用什么复现步骤或测试确认修复有效，以及需要关注的回归影响。明确这些是后续计划，不能写成已经完成的验证。

方案描述用于用户审阅，不直接写入最终修复代码。

### 已测试的假设

只要测试过假设，无论最后是否成立，都必须逐项输出，包含原优先级、假设内容、可证伪预测、测试方法、临时改动、实际观察、结论及回退情况。不要遗漏被排除或仍不确定的假设。

没有测试过假设时，明确说明，并交代结论基于哪些代码或已有证据。

### 其它事项

修复方案对代码改动量较多时，建议用户显式调用 [grill-me](../grill-me/SKILL.md)，进一步完善方案，再确认是否实施。诊断以报告交付结束；只有用户最终确认方案后，才可以另行开始修复。

# 深入追问

持续深入访谈用户，直到双方达成共同理解。将讨论映射为一棵**设计树**：每个决策向下分出依赖它的其他决策。

**每次只问一个问题。** **可提问前沿**是所有前置条件都已确定的决策，也就是无需猜测尚未听到的答案、*现在*就能提出的问题。从前沿选择一个最有助于推进设计的问题，按 Q1、Q2 等连续编号；每题只处理一个独立决策点，不把多个问题合并在一题中。等待用户明确回答后，再提出下一题。

**每题都给出推荐答案和简短理由，优先使用选择题。** 根据实际决策提供 A/B/C/D 等选项，选项应清晰、互斥，数量以足够表达真实选择为准。明确标记推荐选项。只有无法合理列出选项时才使用开放题，仍应给出推荐答案或建议方向及其依据。

**正文必须完整呈现当前问题。** 无论是否使用提问工具，每轮等待用户回答的最终回复正文都必须包含题号、完整问题、推荐答案及简短理由；选择题还必须列出全部选项，让用户仅阅读正文即可作答。不得只把题目和选项放在工具调用、交互卡片或过程更新中，也不得在正文中仅写“推荐 A”“等待选择 Q2”等缺少题目或选项的提示。

如果当前环境提供支持可点击选项的提问工具，可将其作为正文的补充，不能替代正文。每次只传入当前这一个问题；工具与正文中的题号、问题、选项编号和含义、推荐项必须一致。将各选项作为独立条目，并在推荐项的标签中标明“推荐”；工具不提供字母编号时，将 A/B/C/D 写入选项标签。工具返回已接收或发送成功，不代表用户已经看到题目，不能因此省略正文。

用 Markdown 展示选择题时，选项之间必须空一行，让每个选项都是独立的 Markdown 段落。不要将选项挤在同一行、表格或紧凑列表中。实际提问时直接渲染以下格式，不要把整题放进代码块：

```markdown
❓ **Q<n>：<问题标题>**

<一个问题的正文>

**A. <选项内容>**

**B. <选项内容>（推荐）**

**C. <选项内容>**

**D. <选项内容>**

➡️ **推荐：B**。<简短理由>
```

选项字母和推荐项按实际内容调整，不必凑满四项。用户也可以回复选项字母、选项文本，或明确表示采用推荐答案。

用户每次回答后，更新设计树：已确定的决策将前沿向外推进，解锁依赖这些决策的问题。重新计算前沿，再选择一个问题继续。依赖尚未解决决策的问题，留到前置条件明确后再问。

**能从代码库中得到答案的问题，不要问用户。** 提问前先查阅当前对话和相关代码，自行查明可验证的事实，并记录相应依据。能通过查阅代码解决的问题，直接查证，不要求用户代为解释或重复确认。

**无法唯一确定的内容标记为“待决策”，交由用户决定。** 遇到无法由当前对话或代码唯一确定的内容、相互矛盾的结论，或多种合理解释时，明确标记为“待决策”，列出已知依据、冲突点或不同解释，并给出可选方案和推荐答案，按一次一题的规则请用户选择。用户明确决定前，保持“待决策”状态，不把推荐方案或推测记为已确定结论。

当前沿中的问题需要进一步查明环境事实（文件系统、工具等）时，派一个拥有全新上下文窗口的子代理去查明。正在探索的事项属于尚未确定的前置条件，依赖它的问题等待子代理报告；如果其他决策已满足前置条件，可以从中选择一个问题继续，仍须遵守一次一题并等待回答。*决策*属于用户，查明事实是你的工作。

当前沿为空、所有“待决策”事项均已由用户明确决定，且设计树的每个分支都已访问、不再有任何未明说的假设时，会话才完成。在用户确认双方已达成共同理解之前，不要据此采取行动。

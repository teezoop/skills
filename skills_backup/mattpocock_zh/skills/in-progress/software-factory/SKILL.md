**软件工厂**是将工单、PR 和定期安排转化为已合并代码的代理系统，部署在用户选择的远程基础设施上。本技能提供设计软件工厂的语言。讨论或画白板时，只使用以下术语；用户使用*避免使用*中的词时，指出对应的规范术语。

## 任务与运行

**任务（Task）**：
工厂执行的一类工作，定义一次、运行多次，例如审查、探索、实现、渐进收紧标准（ratchet）。任务可以针对工单、PR 或整个代码库。
*避免使用*：job、workflow、action。

**触发器（Trigger）**：
启动一次运行的事件，例如工单跟踪器或 Git 托管平台发生变化、编排器中的时钟，或另一次运行。

**运行（Run）**：
任务从触发到完成、在一个运行器上的一次执行，视为黑盒。一次运行可以直接触发后续运行，也可通过编排器逻辑，或改变工单跟踪器与 Git 托管平台来触发。一次运行从不等待人类：它会结束，随后人类在工单跟踪器或 Git 托管平台上的变更触发新运行。
*避免使用*：session。

**运行器（Runner）**：
执行一次运行的可丢弃机器。即使机器本身长期存在，上面的任何内容也不应跨运行保留：一次运行对以往运行的记忆，只来自工单跟踪器、Git 托管平台和编排器。
*避免使用*：server、host、box、compute、sandbox。

## 服务

**工单跟踪器（Ticket tracker）**：
存放工单，也是工厂的人机交互界面。人类通过提交工单安排工作，在评论中与代理对话，对工单的修改会触发运行。
*避免使用*：issue tracker、ticket manager、project board。

**工单来源（Ticket source）**：
工厂外部、会在工单跟踪器中创建工单的任何事物，例如反馈按钮、监控器、错误跟踪系统或收件箱。
*避免使用*：data source、trigger source、intake。

**Git 托管平台（Git host）**：
存放分支、PR 和审查的位置。
*避免使用*：code host、forge、repo。

**编排器（Orchestrator）**：
接收触发事件、在运行器上启动运行，并记录哪些运行在排队、进行中或已结束的组件。
*避免使用*：dispatcher、scheduler、control plane。

**可观测性平台（Observability platform）**：
运行器发送日志、轨迹和状态的位置，让人类能看到每次运行内部发生了什么。它是可选项：承担运行器或编排器角色的产品，往往已能提供足够信息。在信息被写入工单跟踪器或 Git 托管平台之前，运行从不根据该平台上的信息作决策。
*避免使用*：observability、logs、monitoring、dashboard。

## 设计软件工厂

设计分为两半：**服务**，每项是一个由产品填充的位置；以及**任务**，其运行推动工作在这些服务之间流转。

从用户的问题出发，而不是先从工厂出发：未分诊的工单、等待自动审查的 PR、希望迁移到的更严格自动检查，或无人阅读的缺陷。当用户指出问题或不知道要构建什么时，阅读 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md)，了解解决常见问题的任务。

### 慢慢开始

每个触发器都是加速器。没有刹车的加速器只会变成低质内容喷射器。共有三种刹车：

- **自动检查**：每次运行必须通过的确定性关卡，例如类型、lint、测试。
- **自动审查**：独立运行，在没有先前上下文的情况下，根据代码库规范和工单（如有）阅读差异。
- **人工审查**：合并前由人类阅读 PR；发现的问题转成新的自动检查和更明确的自动审查规则。

每次只添加一个自动触发器，起初限流，例如每十份缺陷报告处理一份，或时钟每天触发一次，且每个 PR 都经过人工审查。随着刹车赢得信任，再逐步加速；每个运行循环都只允许尝试少数几次，然后交给人类。

### 为每个位置选择产品

每项服务都是一个位置。一个产品可以承担多个位置，一台服务器也可以承载多项服务。并列比较三种设计：

| 服务 | 全部使用 GitHub | 使用 Linear 工单 | 自建跟踪器 |
| --- | --- | --- | --- |
| 工单跟踪器 | GitHub Issues | Linear | 自建应用 |
| 工单来源 | 反馈按钮 | 反馈按钮、监控器 | 反馈按钮、监控器 |
| Git 托管平台 | GitHub | GitHub | GitHub |
| 编排器 | GitHub Actions | 自建服务器和数据库 | 自建应用 |
| 运行器 | Actions runner | Actions、E2B、Daytona 或 VPS | 自建应用或沙箱 |
| 可观测性平台 | 不需要，Actions 运行页面已足够 | LLM 轨迹平台 | 自建应用 |

用户为某个位置选择产品时，先阅读该位置的调研概览，再自行研究当前选项。每份概览都按类型分组，并列出决定选择的问题：

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

购买服务，构建任务：任务承载用户的设计，服务是通用的。优先选择现成工单跟踪器，因为它稳健、人们已经熟悉，也容易让外部用户加入。

### 逐项审视任务

对每项任务，回答：

1. 什么会触发它？
2. 它做什么，读写哪些服务？
3. 接下来会触发什么？
4. 人类在哪里重新介入？
5. 什么机制防止两次运行做相同工作？

对每个工单来源，回答：什么机制防止重复提交同一张工单？

每个服务位置都已明确产品（可观测性平台也可以明确选择不设），且每项任务、每个工单来源都回答了所有问题时，设计才完成。

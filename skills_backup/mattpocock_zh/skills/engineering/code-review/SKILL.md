从两个维度审查 `HEAD` 与用户指定固定基点之间的差异：

- **Standards（规范）**：代码是否符合仓库中有文档记录的编码规范？
- **Spec（规格）**：代码是否忠实实现了原始工单或规格？

两个维度由**并行子代理**分别处理，避免相互污染上下文，然后由本技能汇总结果。为每个子代理开启全新的上下文窗口。

用户应已提供问题跟踪系统的信息。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定基点

用户指定的引用就是固定基点，可以是提交 SHA、分支名、标签、`main`、`HEAD~5` 等。如果没有指定，就询问用户。

一次性确定差异命令：`git diff <fixed-point>...HEAD`（使用三个点，从合并基点进行比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定基点能够解析（`git rev-parse <fixed-point>`），且差异非空。错误引用或空差异应在此处报错，而不是等到两个并行子代理中才发现。

### 2. 确定规格来源

按以下顺序寻找原始规格：

1. 提交消息中的工单引用（`#123`、`Closes #45`、GitLab `!67` 等），按问题跟踪系统文档中的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 中与分支名或功能匹配的规格文件。
4. 如果都找不到，询问用户规格在哪里。如果用户表示没有规格，**Spec** 子代理应跳过，并报告“没有可用规格”。

### 3. 确定规范来源

搜索仓库中所有说明代码应如何编写的文件。如果存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，必须列入来源清单。

除仓库记录的规范外，Standards 维度始终包含下述**代码异味基线**：一组固定的 Fowler 代码异味（《重构》第 3 章）。即使仓库没有记录任何规范，这份基线也适用。它受两条规则约束：

- **仓库规范优先。** 仓库明确记录的规范始终优先；如果该规范认可某种基线会标记的做法，就不报告该异味。
- **始终属于判断。** 每种异味都是带标签的启发式判断，例如“可能存在 Feature Envy”，绝不是硬性违规。与此处的其他规范一样，跳过工具已经自动强制执行的事项。

每种异味按“是什么 → 如何修复”列出；将其与差异逐项匹配：

- **Mysterious Name（含糊命名）**：函数、变量或类型的名称无法说明其作用或承载内容。→ 重命名；如果找不到贴切名称，说明设计本身尚不清晰。
- **Duplicated Code（重复代码）**：本次变更中，多个差异片段或文件出现相同的逻辑形态。→ 提取共同结构，让两处都调用它。
- **Feature Envy（依恋他类）**：方法使用另一个对象的数据比使用自身数据更多。→ 将方法移到其依恋的数据所属对象上。
- **Data Clumps（数据泥团）**：同样的几个字段或参数总是一起出现，暗示需要一个新类型。→ 将它们封装为一个类型，并传递该类型。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串表示本应拥有独立类型的领域概念。→ 为该概念定义一个小型专用类型。
- **Repeated Switches（重复条件分支）**：对相同类型的同一组 `switch` 或级联 `if` 在变更中多次出现。→ 使用多态，或让两处共享一张映射表。
- **Shotgun Surgery（霰弹式修改）**：一个逻辑变更迫使差异中的许多文件同时发生零散修改。→ 将共同变化的内容集中到一个模块。
- **Divergent Change（发散式变化）**：同一个文件或模块因多个互不相关的原因被修改。→ 拆分，使每个模块只因一个原因而变化。
- **Speculative Generality（夸夸其谈的通用性）**：为规格中不存在的需求添加抽象、参数或钩子。→ 删除这些内容，恢复内联，直到出现真实需求。
- **Message Chains（消息链）**：调用者依赖不该了解的长链式导航，如 `a.b().c().d()`。→ 在第一个对象的方法后隐藏整段导航。
- **Middle Man（中间人）**：类或函数主要只是向其他对象转发调用。→ 去掉它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）**：子类或实现类忽略或覆盖大部分继承内容。→ 去掉继承，改用组合。

### 4. 并行启动两个子代理

同时发出两个子代理调用，在前台运行，并汇总它们返回的报告。

**Standards 子代理的提示词**应包含：

- 完整差异命令和提交列表。
- 步骤 3 找到的规范来源文件清单，**以及步骤 3 代码异味基线的完整内容**（子代理没有其他途径获取它）。
- 任务说明：“按相关文件或差异片段报告：(a) 差异违反已记录规范的每一处位置，引用规范来源（文件及规则）；(b) 发现的任何基线异味，说明名称并引用差异片段。区分硬性违规与判断性意见：违反已记录规范可能是硬性违规，但基线异味始终是判断性意见，且仓库明确规范优先于基线。跳过工具已经强制执行的事项。控制在 400 词以内。”

**Spec 子代理的提示词**应包含：

- 差异命令和提交列表。
- 规格的路径或获取到的正文。
- 任务说明：“报告：(a) 规格要求但缺失或仅部分实现的需求；(b) 差异中未被要求的行为，即范围扩张；(c) 看似已实现，但实现方式可能不正确的需求。每项发现都引用相应的规格原文。控制在 400 词以内。”

如果没有规格，跳过 Spec 子代理，并在最终报告中说明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下分别呈现两份报告，保留原文或只做轻度整理。**不要**合并或重新排列发现的优先级，因为两个维度本来就是刻意分开的（见“为什么分为两个维度”）。

最后用一句话说明每个维度的发现总数，以及*各自维度内*最严重的问题（如果有）。不要跨维度选出一个总冠军，这正是保持分离所要避免的重新排序。

## 为什么分为两个维度

一项变更可能通过一个维度，却未通过另一个：

- 代码遵循所有规范，却实现了错误的内容 → **Standards 通过，Spec 不通过。**
- 代码完全实现了工单要求，却违反项目约定 → **Spec 通过，Standards 不通过。**

分别报告能够防止一个维度掩盖另一个维度的问题。

# 询问 Matt

不必记住每项技能，直接问即可。

在说明某项技能的作用或建议跳过某个步骤之前，先阅读该技能的 SKILL.md：这里的摘要只用于了解方向。

**流程**是穿过多项技能的一条路径。大多数路径沿同一条**主流程**前进，并有两条**接入路径**汇入。其余技能要么独立使用，要么作为底层术语层。

## 主流程：想法 → 交付

这是大多数工作的路线：你有一个想法，希望把它实现出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你**正在一个工作目录中工作**，就从这里开始：它有状态，会将学到的内容保存在 `GLOSSARY.md` 和 ADR 中。（没有工作目录？改用“独立技能”中的 `/grill-me`。两者都运行相同的 `/grilling` 基础流程；`grill-with-docs` 会留下书面记录，因此只要有仓库可存放记录，它就是两者中更合适的选择。）
2. **分支：所有问题都能通过对话确定吗？** 如果某个问题需要可运行的答案，例如状态、业务逻辑，或必须看到才能判断的 UI，就绕道原型，并在两个方向都使用 **`/handoff`** 衔接（原型位于自己的目录，这正是 `/handoff` 的用途；见“阶段边界”）：
   - 用 **`/handoff`** 交出去，再根据该文件开启全新会话；
   - 用 **`/prototype`** 通过一次性代码回答问题；
   - 用 **`/handoff`** 交回学到的内容，并在原始想法讨论中引用。
3. **分支：实现需要多个会话吗？**
   - **需要** → 先 **`/to-spec`**，将讨论转为规格；再 **`/to-tickets`**，拆成曳光弹式工单，各自声明**阻塞依赖**。随后有两种处理方式：
     - 每张工单执行一次 **`/implement`**，**工单之间用 `/clear` 清空上下文**。本地跟踪系统中，每张工单一个文件，位于 `.scratch/<feature>/issues/`，手动按阻塞项优先的顺序处理；实际跟踪平台中，依赖成为原生阻塞链接，任何阻塞项已完成的工单都可领取。每张工单是自包含的，上一张工单的上下文可以丢弃。
     - 对整份规格执行一次 **`/implement-spec`**。它将工单视为**任务图**，在就绪的**可执行前沿**上并行运行实现子代理，并将全部工作汇入一个**集成分支**。如果你更想编排整个实现，而不是逐张驱动工单，就使用它。
   - **不需要** → 直接在当前上下文窗口中执行 **`/implement`**。

   两种方式都通过 **`/tdd`** 构建代码，每次一个红灯到绿灯的切片，最后通过 **`/code-review`** 对差异做双维度审查（Standards + Spec）。`/implement` 会为每张工单执行这两项；`/implement-spec` 的每个实现子代理执行 `/tdd`，最后对整个集成分支执行一次 `/code-review`。如果只想先写测试实现一个具体行为，而不需要完整规格，可以单独使用 **`/tdd`**；想相对固定基点审查分支或 PR 时，可以单独使用 **`/code-review`**。

   工作通过 pull request 提交时，**`/pr`** 负责组织正文：用最小图示说明变更，以修改前后的证据说明其有效性，并判断是单向门还是双向门决策。它可由模型调用，因此代理写 PR 时会使用它。

4. **`/retro`** 闭合反馈循环。完成实现后，尤其是过程不顺利时，它回顾会话，为代理的**工作环境**而非代码提出改进：导航指针、自动检查、`/code-review` 执行的编码规范、引导文件和工具。机械性错误转为确定性检查，判断性问题转为编码规范，让下一次实现从更好的环境出发。

### 上下文管理

将步骤 1 至 3 保持在**一个不中断的上下文窗口**中，直到 `/to-tickets` 之后才压缩或清空，确保深入访谈、规格和工单建立在同一套思考上。之后每次 `/implement` 都从全新上下文开始，根据工单工作。`/retro` 应在它所复盘的会话中、清空前执行；若已清空，改为向它提供该会话的日志。

限制来自**[智能区间（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**，即模型仍能保持敏锐推理的窗口，先进模型约为 150k token。如果在 `/to-tickets` 前就接近该区间，不要在能力下降后强行继续；在最近的阶段边界执行 `/compact`，然后继续，见“阶段边界”。

## 接入路径

这些起始情境会产生工作，随后汇入主流程。

- **缺陷和请求积压** → **`/triage`**。它让工单经过分诊角色，产出可交给代理的工单，之后由 **`/implement`** 处理。

  分诊只用于**不是你创建的**工单：缺陷报告、外来功能请求及其他原始请求。`/to-tickets` 生成的工单已经可以交给代理，**不要再分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于疑难问题：一眼看不出原因的缺陷、间歇性失败，以及在两个已知正常状态之间引入的回退。在获得**紧凑反馈循环**之前，它拒绝提出理论；该循环应是一条已经能够针对*这个*缺陷报红的命令。随后修复并加入回归测试。修复完成后，在同一会话运行 **`/retro`**，检查什么措施本可防止缺陷；如果真正发现是缺少合适接缝、无法用测试锁定缺陷，就应交给 **`/improve-codebase-architecture`**。

- **庞大而模糊的工作，例如全新项目或大功能，无法在一个会话内容纳** → **`/wayfinder`**，这是这里认知负担最高的流程。当从当前位置通往目标的路径尚不可见时，它在问题跟踪系统中绘制由**决策工单**组成的**共享地图**，逐个解决，产出**决策，而非交付物**，直到迷雾退去、道路清晰。**`/grill-with-docs`** 打磨一个会话能容纳的想法；wayfinder 处理的是无法容纳的想法。它更慢、更密集，所以仅在这种情况下使用，绝不要用于范围已经清晰的功能。

  地图清晰后，**它交接，不实现**：从 **`/to-spec`** 汇入主流程，将地图中相互链接的决策收束成可实现计划，再照常执行 `/to-tickets` 和 `/implement`。直接从地图跳进 `/implement`，会跳过收束并丢掉链接细节，因此只有最终发现工作确实很小时，才直接实现。

## 代码库健康

这不是功能开发，而是日常维护。

- **`/improve-codebase-architecture`** 可在有空时运行，让代码库适合代理工作。它寻找**深化机会**；选中一个后，就产生了可从 `/grill-with-docs` 进入主流程的*想法*。它负责调查并找到候选项；下文的 **`/codebase-design`** 则是设计所选方案的工作台。

## 底层术语

两项可由模型调用的参考技能运行在其他技能*之下*，各自是相应术语的唯一权威来源。当问题在于**用词**而非流程时，直接查阅；也可以由上层技能引入。

- **`/domain-modeling`**：打磨项目的*领域*语言，质疑含糊术语，消除多义词（例如“account”承担三种职责），将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 驱动的主动实践，让 `GLOSSARY.md` 始终保持为干净的术语表。
- **`/codebase-design`**：设计模块*形态*所需的深模块术语，包括模块、接口、深度、接缝、适配器、投入收益、局部性。目标是在清晰接缝的小接口后面封装大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 阶段边界

**阶段**是会话中的一块工作，例如深入访谈、实现或 QA。两个阶段的**边界**有五种选择，而如何选是这张地图中最模糊的决策：

- **继续**：保持当前上下文。没有成本，也不丢信息。
- **`/clear`**：当这里的内容对下一步不再重要时，清空窗口。
- **`/handoff`**：写出可携带的 Markdown 文件。用途很窄，仅用于**新的代理运行环境**、**新目录**、**同事交接**，或在**阶段中途**分叉支线任务。它提供的是可移植性。
- **子代理**：将范围明确的小任务交给独立窗口，并收回报告。
- **`/compact`**：压缩当前上下文，并据此开启新会话。它是决策树底部的**默认选项**，而不是第一选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)，了解有序决策树：五个问题、每个分支的理由，以及为什么重新读取一手资料的成本，意味着应先排除**继续**。在边界*当下*作出决定；阶段中途应继续，或把剩余工作拆给子代理。

## 独立技能

这些技能完全独立于主流程。

- **`/grill-me`**：与 `/grill-with-docs` 相同的持续深入访谈，但**无状态**，不在本地保存内容，也不创建 `GLOSSARY.md`。适用于**不在工作目录中工作**的情况，例如打磨计划、设计、文章或任何没有底层仓库的事项。如果在工作目录中，就改用 `/grill-with-docs`：它运行相同访谈并留下书面记录，因此更合适。
- **`/grilling`**：访谈基础流程本身，包括轮次、可提问前沿、事实由代理查明、决策由用户决定。`/grill-me` 和 `/grill-with-docs` 是两个命名入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有你希望直接使用不带封装的访谈时，才单独调用。
- **`/prototype`**：一个小型一次性程序，用来回答一个设计问题，例如状态模型是否合理、UI 应长什么样。“一次性”约束的是代码编写方式，并不意味着必须销毁：答案融入正式代码，原型自身作为**一手资料**保留在 main 之外的 `prototype/<name>` 分支上，并从实现工单链接过去。它是主流程步骤 2 的绕行，但任何难以在纸面上确定的设计问题都可使用。
- **`/research`**：将资料阅读交给**后台代理**。它根据**一手来源**研究问题，再在仓库中留下有引用的 Markdown 文件；它阅读时，你可以继续工作。该文件可以从 `/grill-with-docs` 带*入*主流程，因为研究为思考提供材料，而不是替代思考。
- **`/to-questionnaire`**：当阻塞信息不在你脑中，也不在代码库，而在**另一个人脑中**时，生成问卷交给对方填写。它与 `/grill-me` 相反：不是围绕主题访谈你，而是询问**发送安排**，即发给谁、需要什么，再用问题瞄准知识缺口。回收的内容可供 `/grill-with-docs` 或 `/to-spec` 使用。
- **`/wizard`**：用于只有**人类**能完成的步骤，例如配置基础设施、凭据或 CI 密钥、操作陌生第三方面板、执行一次性迁移或切换。它生成交互式 bash 脚本，打开各 URL、收集各值，并写入 `.env` 和 GitHub secrets，避免每次都重新向代理解释流程。它可由模型调用，代理遇到只有你能跨越的障碍时便会使用。如果代理能自行完成，就应该自己做；此技能只用于确实需要人在环中的场景。
- **`/wait-what`**：纠正没有讲明白的消息。可在对话中途、任何其他技能内部使用；代理会补充你缺少的上下文，用浅显英语和 `GLOSSARY.md` 中的词汇重新说明刚才内容。它用于事后修正；`/grill-with-docs` 则是事前预防，因为尽早约定共同语言可以避免术语障碍出现。
- **`/teach`**：跨多个会话学习概念，将当前目录作为有状态的工作区。
- **`/writing-for-agents`**：编写供代理消费的文档的参考，包括技能、AGENTS.md 及被引用的文档。

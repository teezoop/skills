一个模糊想法出现了，大到无法放进单次代理会话，而且笼罩着迷雾：从当前位置通往**目标**的路径尚不可见。寻路是在寻找这条路，而不是一头冲向目标。本技能在仓库的问题跟踪系统上绘制**共享地图**，再逐个处理其中的**决策工单**。这些工单解决的是决策问题，而不是要执行的实现切片；持续推进，直到路线清晰。

每项工作的目标不同，明确命名目标是绘图的第一步，它决定每张工单的形态。目标可能是一份供交接与迭代的规格、开始计划前必须确定的决策，也可能是就地实施的变更，例如数据结构迁移。地图与领域无关：工程工作、课程内容等，只要符合这种形态都可使用。

## 规划，而非执行

Wayfinder 默认用于**规划**：每张工单解决一项决策；当路径清晰、执行前不再有待定决策时，地图就完成了。你产生“直接动手做”的冲动，通常意味着已经到达地图边缘，应当交接。具体工作可以在其**备注**中覆盖这一规则，让执行本身进入地图；没有此约定时，就产出决策，而非交付物。

## 按名称引用

每张地图和工单都是 issue，因此有一个**名称**，即标题。在人类会阅读的一切内容中，包括过程说明和地图的“已作出的决策”，都用名称引用，而不是裸 ID、编号或 slug。满屏 `#42, #43, #44` 很难读，名称则能一眼理解。ID 和 URL 并未消失，而是包在名称的链接中，绝不代替名称本身。

## 地图

地图是本仓库问题跟踪系统中的一个 issue，标记为 `wayfinder:map`，是权威产物；它的工单都是该地图的子 issue。

地图是**索引**，不是内容仓库。它列出已作出的决策，指向保存细节的工单；每项决策只保存在一个地方，即对应工单。地图只概括并链接，不重复正文。

**地图、子工单、阻塞关系及前沿查询的实际存放和表达方式取决于跟踪系统。** 用户应已提供问题跟踪系统信息；如果没有，请让用户运行 `/setup-matt-pocock-skills`。查阅跟踪系统文档中的“Wayfinding operations”一节，了解*本*仓库如何表达这些内容。如果尚未提供跟踪系统，默认采用本地 Markdown 跟踪方式。

### 地图正文

这是整张地图的低分辨率视图，每次会话加载一次。不列出未关闭工单；它们作为未关闭的子 issue，通过查询发现。

### 工单

每张工单都是地图的**子 issue**，以跟踪系统的 issue ID 作为身份。正文描述问题，规模应适合一个 100K token 的代理会话：

```markdown
## 问题

<本工单要解决的决策或调查>
```

每张工单带有 `wayfinder:<type>` 标签，类型为 `research`、`prototype`、`grilling`、`task` 之一，见[工单类型](#ticket-types)。地图及其工单只带 `wayfinder:` 标签，绝不添加 `ready-for-agent` 等分诊标签，因为它们是决策，而非实现工作。

每次会话在任何工作之前，**首先**将工单分配给推动地图的开发者，以此**领取**工单，让并发会话跳过它。这个负责人*就是*领取标记：未关闭且未分配的工单才是未领取。

阻塞关系使用跟踪系统的**原生**依赖关系。这很重要，因为它能在平台自己的 UI 中*可视化*呈现前沿，让人类无需打开地图就能看出哪些工作可领取。只有没有原生阻塞关系的平台，才回退到正文约定。阻塞某工单的所有工单都已关闭时，该工单才是**未被阻塞**的；**前沿**则是所有未关闭、未被阻塞且未领取的子工单，即已知区域的边缘。

答案不写入正文，而是在解决时记录，见[按地图推进](#work-through-the-map)。解决工单过程中创建的资源，从 issue 中链接，不要直接粘贴进去。

## 工单类型

每张工单要么是 **HITL**（人在环中，*与*能代表自己发言的人类共同处理），要么是 **AFK**（代理独立推进）。HITL 工单只能通过真实的实时交流解决，代理绝不能代替人类发言；追问代理自己回答自己的问题，就违背了这一点。

- **Research，研究（AFK）**：阅读文档、第三方 API 或知识库等本地资源，查明某项决策所等待的事实。由调用 Skill 工具加载 "research" 的子代理解决。需要当前工作目录之外的知识时使用。
- **Prototype，原型（HITL）**：通过调用 Skill 工具加载 "prototype"，制作廉价、粗略、具体的产物，例如提纲、初步方案、占位实现或 UI / 逻辑代码，供人类反馈，从而提高讨论保真度。将原型作为资源链接。核心问题是“应该长什么样”或“应该如何表现”时使用。
- **Grilling，深入追问（HITL）**：对话，是默认类型。始终调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"。
- **Task，任务（HITL 或 AFK）**：作出*决策*前必须完成的手动工作，本身没有需要决定、制作原型或研究的内容，但不完成就无法继续讨论。例如注册服务以评估其 API、开通访问权限、搬移数据以便观察其结构。这是唯一真正*执行*而非决策的类型，它存在的理由是解锁决策，而非交付最终目标。代理能独立完成时独立推进（AFK）；否则给人类一份精确检查清单（HITL）。工作完成后解决工单；答案记录做了什么，以及后续工单依赖的事实，例如凭据位置、新 URL、行数。

## 战争迷雾

地图是*刻意*不完整的：不要绘制尚看不见的内容。现有工单之外是**战争迷雾**，即你知道将会出现、但还无法明确的决策和调查，因为它们依赖尚未解决的问题。解决一张工单会扫清前方迷雾，将如今能明确描述的部分逐个转成新工单，直到通往目标的路线清晰且不再有工单。

地图的**尚未明确**一节记录这些模糊内容：可能的问题、之后需重新查看的区域。这是*通往*目标的未发现前沿，所有内容都在范围内，只是还不足以明确成工单。能看清多少就写多少，可以很粗略，也可以很完整；它同时帮助协作者理解工作方向。

**迷雾还是工单？** 判断标准是现在能否准确陈述问题，*不是*现在能否回答。

- **写成工单**：问题已经清晰，即使被阻塞、暂时无法行动。
- **留在尚未明确**：尚无法准确表达问题。不要预先把迷雾切成工单大小；它比工单更粗，当前沿到达时，一片迷雾可能转成多张工单，也可能一张都不需要。

**尚未明确**不包含已确定事项（已作出的决策）、已有的活动工单，或范围外事项（见下一节）。

## 范围之外

迷雾只沿着*通往*目标的方向存在。目标决定范围，因此超出目标的工作属于**范围之外**，不是迷雾，也不属于**尚未明确**。在地图上为它设置独立的**范围之外**一节，记录你已明确排除在*本次*工作之外的内容。它被放在这里，是因为范围，而非清晰程度。

范围外工作绝不转为工单，因为前沿到目标处就停止。只有重新定义目标时，它才可能回来，而且应作为新工作，而非恢复当前工作。

将事项排除在范围外是范围界定，不是路线上的一步。如果已有工单后来被发现位于目标之外，例如绘图时范围划错，或被某项结论揭示，就**关闭它**，使其明确退出前沿；在**范围之外**一节留一行，概括内容、说明为何超范围，并链接已关闭工单。不要放进**已作出的决策**，因为那里记录实际走过的路线，范围边界不是路线的一步。

## 调用方式

两种模式。无论哪种，**每次会话最多解决一张工单**，研究工单除外。

### 绘制地图

用户带着一个模糊想法调用。

1. **命名目标。** 调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"，确定这张地图要通向什么规格、决策或变更。目标决定范围，因此先确定目标。
2. **绘制前沿。** 再次追问，这次采用**广度优先**：在整个空间展开，而不是深挖单条线，找出未决事项和现在可走的第一步。**如果没有发现迷雾**，即通往目标的路线已清晰，且整个过程小到一个会话就能完成，就不需要地图。停下来，询问用户希望如何继续。
3. **创建地图**，标签为 `wayfinder:map`：填写目标和备注，已作出的决策留空，将迷雾概述在**尚未明确**中。
4. **将现在能明确的工单创建为地图的子 issue**，然后在**第二遍**连接阻塞关系，因为 issue 必须先有 ID 才能相互引用。交叉引用也在这一遍使用真实 ID 写入：占位 `#<n>` 会自动链接到不相关的 issue。连线会将工单分为前沿和被阻塞项；尚不能明确的内容继续留在迷雾，即**尚未明确**一节。
5. **启动研究子代理。** 对刚创建的每张 `research` 工单，启动拥有全新上下文窗口的子代理，调用 Skill 工具加载 "research" 并行解决。将研究结果保存在一次性 `research/<name>` 分支，并从工单给出上下文指针。推送分支，但不创建 PR，因为该分支永不合并。
6. 停止：绘图就是一个会话的工作，不在本会话中手动解决其他工单。

<a id="work-through-the-map"></a>

### 按地图推进

用户提供地图 URL 或编号调用。工单是**可选**参数：没有指定时，由你选择下一项决策，而非让用户选择。

1. 加载**地图**的低分辨率视图，而不是所有工单的正文。
2. 选择工单。用户指定了就使用它，否则按顺序取第一张前沿工单。**领取它**：任何工作前先分配给自己。
3. 根据 `wayfinder:<type>` 标签指定的类型解决，见[工单类型](#ticket-types)。读取标签，不要只看正文，因为正文从不声明类型。**按需放大查看**：需要时获取相关工单或已关闭工单的完整正文；调用 Skill 工具加载“备注”（原文 `## Notes`）块指定的技能。拿不准时，调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"。
4. 记录结论：以**解决评论**发布答案，**关闭** issue，并在地图的“已作出的决策”中**追加上下文指针**。
5. 添加新浮现的工单，先创建再连线；将答案使之明确的迷雾转成工单，并从**尚未明确**中移除已转化部分，让内容只存在于新工单。如果答案揭示本工单或其他工单位于目标之外，就**排除在范围外**，而不是作为路线步骤解决。如果该决策使地图其他部分失效，更新或删除那些工单。

用户可能并行运行未被阻塞的工单，因此要预期其他会话也在同时编辑跟踪系统。

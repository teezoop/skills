# 缺陷诊断

用于疑难缺陷的一套工作纪律。只有明确说明理由时，才可以跳过某个阶段。

探索代码库时，阅读 `GLOSSARY.md`（如果存在），建立对相关模块的清晰认知，并检查所修改区域中的 ADR。

## 脱敏

本技能要求展示命令、输出及捕获的产物。**先隐去所有秘密信息**：将其替换为 `<REDACTED>`。让循环通过环境变量获取凭据，使凭据保留在环境中，而不出现在展示内容里。捕获的产物可能带有认证头，只引用真正提供诊断信号的行。

如果脱敏后的输出不足以诊断缺陷，明确说明并询问用户。

## 阶段 1：构建反馈循环

**这就是本技能的核心。** 其他一切只是机械操作。只要你拥有针对该缺陷的**紧凑**通过或失败信号，能够在*这个*缺陷出现时变红，就能找到原因；二分定位、假设检验和插桩都只是使用这个信号。如果没有这样的信号，再怎么盯着代码看也无济于事。

在此投入远超其他环节的精力。**积极尝试，发挥创造力，不轻言放弃。**

### 构建方式，大致按以下顺序尝试

1. 在能够触及缺陷的接缝处编写**失败测试**：单元、集成或端到端测试皆可。
2. 对正在运行的开发服务器编写 **curl 或 HTTP 脚本**。
3. 使用固定输入**调用 CLI**，将标准输出与已知正确的快照做差异比较。
4. 使用**无头浏览器脚本**（Playwright / Puppeteer）驱动 UI，并对 DOM、控制台或网络进行断言。
5. **回放捕获的轨迹。** 将真实网络请求、载荷或事件日志保存到磁盘，再单独通过相关代码路径回放。
6. **一次性测试装置。** 启动系统的最小子集，例如单个服务和模拟依赖，用一次函数调用触发缺陷路径。
7. **属性测试或模糊测试循环。** 如果缺陷是“有时输出错误”，运行 1000 个随机输入并查找失败模式。
8. **二分定位装置。** 如果缺陷出现在两个已知状态（提交、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”，使其能够通过 `git bisect run` 执行。
9. **差分循环。** 用相同输入分别运行旧版本与新版本，或两套配置，再比较输出。
10. **人在环中的 bash 脚本（HITL）。** 最后手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 引导*人的操作*，让循环仍保持结构化，并将捕获的输出反馈给你。

构建正确的反馈循环，缺陷就已经解决了九成。

### 收紧循环

将循环当作产品打磨。拥有*一个*循环后，继续**收紧**它：

- 能否更快？例如缓存准备工作、跳过无关初始化、缩小测试范围。
- 能否让信号更明确？断言具体症状，而不只是“没有崩溃”。
- 能否更确定？固定时间、设置随机种子、隔离文件系统、冻结网络条件。

一个耗时 30 秒且不稳定的循环，几乎不比没有循环好；一个 2 秒完成且确定的循环才足够紧凑，是调试的强大能力。

### 非确定性缺陷

目标不是每次都能干净复现，而是**提高复现率**。将触发操作循环 100 次、增加并行、施加压力、缩小时序窗口、插入休眠。复现率 50% 的偶发缺陷可以调试，1% 的则不行；持续提高复现率，直到足以调试。

### 确实无法构建循环时

停下来并明确说明。列出已尝试的方法。向用户请求：(a) 能复现问题的环境访问权限；(b) 已脱敏的捕获产物，例如 HAR 文件、日志转储、核心转储或带时间戳的录屏；或 (c) 添加临时生产环境插桩的权限。**不要**在没有循环的情况下继续提出假设。

### 完成标准：紧凑且能变红的循环

当循环足够**紧凑**且**能够报红**时，阶段 1 才完成：你能指出**一条命令**，可以是脚本路径、测试调用或 curl；你**至少已实际运行过一次**（展示脱敏后的调用和输出），且它满足：

- [ ] **能够报红**：驱动实际的缺陷代码路径，并断言**用户描述的确切症状**，使其在缺陷存在时报红，修复后变绿。不是简单的“运行没有报错”，而是必须能够*捕获这个具体缺陷*。
- [ ] **确定性**：每次运行给出同样结论；对于偶发缺陷，采用前述固定且较高的复现率。
- [ ] **快速**：耗时以秒计，而非分钟。
- [ ] **代理可运行**：可以无人值守执行；必须有人参与时，只通过 `scripts/hitl-loop.template.sh` 引入。

如果这条命令尚不存在，你就开始读代码构建理论，**停下来：直接跳到假设，正是本技能要防止的失败方式。** 没有能够报红的命令，就不能进入阶段 2。

## 阶段 2：复现并最小化

运行循环，观察缺陷出现时它变红。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是碰巧发生在附近的另一种失败。找错缺陷，就会做错修复。
- [ ] 多次运行都能复现；非确定性缺陷也应达到足以调试的复现率。
- [ ] 已捕获确切症状，例如错误消息、错误输出或性能变慢的时间指标，供后续验证修复是否真正解决问题。

### 最小化

一旦报红，就将复现场景缩小到**仍会报红的最小场景**。每次只删减**一个**输入、调用者、配置、数据或步骤；每次删减后重跑循环，只保留导致失败所必需的内容。

这样做的原因是：最小复现能够缩小阶段 3 的假设空间，减少可怀疑的活动部件，并在阶段 5 成为清晰的回归测试。

当**所有剩余元素都不可或缺**，删除其中任意一个都会使循环变绿时，最小化完成。

必须同时完成**复现和最小化**，才能继续。

## 阶段 3：提出假设

在测试任何假设之前，先生成**按优先级排序的 3 至 5 个假设**。只提出一个假设，容易锚定在第一个貌似合理的想法上。

每个假设都必须**可证伪**，说明它作出了什么预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让缺陷消失，或 <改变 Z> 会让缺陷更严重。”

如果无法说出预测，这个假设就只是感觉：丢弃它，或进一步明确。

**测试前，先向用户展示排序后的清单。** 用户往往掌握能够立即调整排序的领域知识，例如“我们刚部署了与第 3 项有关的变更”，或者知道哪些假设已被排除。这个检查点成本很低，却能节省大量时间。不要因此阻塞；如果用户暂时不在线，就按你的排序继续。

## 阶段 4：插桩

每个探针都必须对应阶段 3 的某项具体预测。**一次只改变一个变量。**

工具优先级：

1. 环境支持时，优先**调试器或 REPL 检查**。一个断点胜过十条日志。
2. 在能够区分假设的边界处添加**定向日志**。
3. 绝不采用“记录一切再 grep”的方式。

**为每条调试日志添加唯一前缀**，例如 `[DEBUG-a4f2]`。结束时一次 grep 即可清理。无标签日志容易遗留，带标签日志容易移除。

**性能分支。** 对性能回退，日志通常不是正确工具。应先建立基线测量，例如计时装置、`performance.now()`、性能分析器或查询计划，再二分定位。先测量，后修复。

## 阶段 5：修复与回归测试

在**修复前**编写回归测试，但前提是存在**正确的测试接缝**。

正确接缝应让测试以实际调用点上的方式覆盖**真实缺陷模式**。如果唯一可用的接缝过浅，例如缺陷需要多个调用者，却只有单调用者测试，或单元测试无法复现触发缺陷的调用链，那么在那里写回归测试只会带来虚假的信心。

**如果没有正确接缝，这本身就是发现。** 记录它：代码库架构正在阻止你用测试锁定缺陷，并将其标记为下一阶段要处理的事项。

如果存在正确接缝：

1. 将最小复现转成该接缝处的失败测试。
2. 观察测试失败。如果你通过修改代码或测试数据强行制造红灯，先与干净副本进行 `diff`，证明修改确实生效，再相信结果。
3. 应用修复。
4. 观察测试通过。
5. 针对原始、未最小化的场景，重跑阶段 1 的反馈循环。

## 阶段 6：清理

宣布完成前，必须确认：

- [ ] 原始复现不再出现问题，已重跑阶段 1 的循环。
- [ ] 回归测试通过，或已记录缺少正确接缝的情况。
- [ ] 所有 `[DEBUG-...]` 插桩已移除，通过 `grep` 搜索前缀确认。
- [ ] 一次性原型已删除，或已移到明确标记的调试目录。
- [ ] 在提交或 PR 消息中说明最终验证成立的假设，便于下一位调试者学习。

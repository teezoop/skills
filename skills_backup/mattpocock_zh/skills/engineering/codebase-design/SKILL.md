# 代码库设计

设计**深模块**：在简小接口背后提供大量行为，将接口置于清晰的接缝处，并能通过该接口测试。在任何代码设计或结构调整中，都使用这些术语和原则。目标是让调用者获得更高投入收益，让维护工作保持局部性，并让所有人都能方便测试。

## 术语表

准确使用以下术语，不要替换成“component”“service”“API”或“boundary”。保持语言一致正是目的所在。

**模块（Module）**：任何同时具有接口和实现的事物。刻意不限定规模，可以是函数、类、包，也可以是跨层切片。*避免使用*：unit、component、service。

**接口（Interface）**：调用者为正确使用模块而必须知道的一切：不仅包括类型签名，还包括不变量、顺序约束、错误模式、必需配置及性能特征。*避免使用*：API、signature；这些词过于狭窄，只指类型层面的表面。

**实现（Implementation）**：模块内部的代码内容。它与**适配器（Adapter）**不同：小适配器可以有庞大的实现（例如 Postgres 仓库），大适配器也可以只有很小的实现（例如内存中的假实现）。讨论接缝时使用“适配器”，其他时候使用“实现”。

**深度（Depth）**：接口带来的投入收益，即调用者或测试每学习一单位接口，能够使用多少行为。在简小接口后面封装大量行为的模块是**深模块**；接口几乎和实现一样复杂的模块是**浅模块**。

**接缝（Seam）**（Michael Feathers）：无需编辑该位置的代码就能改变行为的位置，也是模块接口所在的*位置*。接缝放在哪里是一个独立设计决策，不同于接缝背后应放什么。*避免使用*：boundary，它容易与 DDD 的限界上下文混淆。

**适配器（Adapter）**：在某个接缝处满足接口的具体事物。描述的是*角色*（填补哪个位置），而不是内部材料（里面是什么）。

**投入收益（Leverage）**：调用者从深度中获得的回报。每学习一单位接口，就获得更多能力。一份实现可以让 N 个调用点和 M 个测试受益。

**局部性（Locality）**：维护者从深度中获得的回报。变更、缺陷、知识和验证集中在一处，而不是散落在各个调用者中。修复一次，处处生效。

## 深模块与浅模块

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│      深层实现       │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│             大接口              │  ← 方法多，参数复杂
├─────────────────────────────────┤
│            薄层实现             │  ← 只是透传
└─────────────────────────────────┘
```

设计接口时，询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂性？

## 原则

- **深度是接口的属性，而不是实现的属性。** 深模块内部可以由小型、可模拟、可替换的部件组成，只是这些部件不属于接口。模块除了接口上的**外部接缝**，也可以有**内部接缝**，后者是实现的私有部分，供模块自身的测试使用。
- **删除测试。** 想象把模块删除。如果复杂性随之消失，说明它只是透传层；如果复杂性重新散布到 N 个调用者中，说明它有存在价值。
- **接口就是测试面。** 调用者和测试穿过同一个接缝。如果你想越过接口测试内部，模块的形态很可能不对。
- **一个适配器意味着假想接缝，两个适配器才意味着真实接缝。** 除非确实存在需要跨接缝变化的事物，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试自然而然地成立：

1. **接收依赖，而不是创建依赖。**

   ```typescript
   // 容易测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 容易测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **较小的表面范围。** 方法越少，需要的测试越少；参数越少，测试准备越简单。

## 概念关系

- 一个**模块**恰有一个**接口**，即它呈现给调用者和测试的表面。
- **深度**是**模块**的属性，以其**接口**为参照衡量。
- **接缝**是**模块接口**所在的位置。
- **适配器**位于**接缝**处，并满足**接口**。
- **深度**为调用者产生**投入收益**，为维护者产生**局部性**。

## 不采用的表述

- **将深度定义为实现行数与接口行数之比**（Ousterhout）：这会鼓励给实现灌水。这里改用接口带来的投入收益衡量深度。
- **将“接口”仅理解为 TypeScript 的 `interface` 关键字或类的公开方法**：过于狭窄；这里的接口包含调用者必须知道的全部事实。
- **“Boundary”**：容易与 DDD 的限界上下文混淆。请使用**接缝**或**接口**。

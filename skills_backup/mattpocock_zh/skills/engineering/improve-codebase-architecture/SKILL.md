# 改进代码库架构

揭示架构中的阻力，并提出**深化机会**：通过重构将浅模块变成深模块。目标是提高可测试性和 AI 的代码导航能力。

本命令以项目的领域模型为*依据*，并建立在共同的设计术语之上：

- 调用 Skill 工具加载 "codebase-design"，获取架构术语（**模块**、**接口**、**深度**、**接缝**、**适配器**、**投入收益**、**局部性**）及其原则，包括删除测试、“接口就是测试面”、“一个适配器是假想接缝，两个才是真实接缝”。每项建议都应准确使用这些术语，不要转而使用“component”“service”“API”或“boundary”。
- `GLOSSARY.md` 中的领域语言为合适的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决策。

## 流程

### 1. 探索

**先确定范围，再扫描：遵循 YAGNI。** 深化模块的收益在于让未来修改它更容易，因此应更加重视近期发生过变化的代码区域。先决定*看哪里*，再开始看：

- 如果用户指定了方向，例如某个模块、子系统或痛点，就按此方向开展，跳过下述推断。
- 否则，回看足够长的一段提交历史（`git log --oneline`），找出反复出现的热点文件和区域，优先关注这些路径。如果变化分散、没有明显热点，再扩大范围。

先阅读项目领域术语表（`GLOSSARY.md`）和相关区域中的 ADR。

随后启动一个拥有全新上下文窗口的子代理，遍历代码库。不要套用僵硬的启发式规则；自然探索，并记录遇到阻力的位置：

- 理解一个概念时，哪里需要在许多小模块间来回跳转？
- 哪些模块是**浅模块**，接口几乎和实现一样复杂？
- 哪里只是为了方便测试而提取了纯函数，真实缺陷却藏在调用方式中，缺少**局部性**？
- 哪里存在紧密耦合的模块，细节越过接缝泄漏？
- 哪些代码没有测试，或难以通过现有接口测试？

对怀疑过浅的模块应用**删除测试**：删除它会让复杂性集中起来，还是仅仅搬家？“会集中”就是你要找的信号。

### 2. 用 HTML 报告呈现候选项

将一个独立 HTML 文件写入操作系统临时目录，避免将报告放进仓库。从 `$TMPDIR` 获取临时目录，不存在时使用 `/tmp`（Windows 使用 `%TEMP%`）。写入 `<tmpdir>/architecture-review-<timestamp>.html`，确保每次生成新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告知绝对路径。

报告通过 CDN 引入 **Tailwind** 来处理布局与样式；当图、流程或时序能可靠表达结构时，通过 CDN 引入 **Mermaid** 绘图。将 Mermaid 与手工 CSS/SVG 图示结合：关系适合图结构时，例如调用图、依赖或时序，使用 Mermaid；需要更具版面表现力的形式时，例如体块图、剖面图或折叠动画，使用手工 div/SVG。每个候选项都提供**改造前后可视化**。充分使用图示。

每个候选项渲染成一张卡片，包含：

- **文件**：涉及哪些文件或模块。
- **问题**：当前架构为什么产生阻力。
- **方案**：用浅显英语描述将改变什么。
- **收益**：从局部性、投入收益以及测试如何改进来说明。
- **改造前后图示**：并排、自行绘制，展示原有的浅层结构和深化后的结构。
- **推荐强度**：用徽章显示 `Strong`（强烈推荐）、`Worth exploring`（值得探索）或 `Speculative`（推测性建议）之一。

报告末尾提供**首要推荐**一节，说明应先处理哪个候选项，以及原因。

**领域用语遵循 GLOSSARY.md，架构用语遵循 `/codebase-design`。** 如果 `GLOSSARY.md` 定义了“Order”，就说“Order 接入模块”，不要说“FooBarHandler”，也不要说“Order service”。

**与 ADR 冲突**：如果候选项违背现有 ADR，只有在实际阻力足以值得重新审视该 ADR 时才提出。在卡片中明确标记，例如警告：“与 ADR-0007 冲突，但值得重新讨论，因为……”。不要列出 ADR 禁止的每一种理论重构。

完整 HTML 骨架、图示模式和样式指导见 [HTML-REPORT.md](HTML-REPORT.md)。

此时**不要**提出接口方案。写完文件后，询问用户：“你想进一步探索其中哪一个？”

### 3. 深入追问循环

用户选定候选项后，调用 Skill 工具加载 "grilling"，与用户共同遍历决策树：约束、依赖、深化后模块的形态、接缝背后放什么，以及哪些测试继续保留。

决策一旦明确，就即时完成相应更新；调用 Skill 工具加载 "domain-modeling"，在过程中持续维护领域模型：

- **深化模块的命名使用了 GLOSSARY.md 中不存在的概念？** 将术语加入 `GLOSSARY.md`；文件不存在时按需创建。
- **对话中澄清了一个含糊术语？** 当场更新 `GLOSSARY.md`。
- **用户因关键理由拒绝候选项？** 提议编写 ADR，例如：“要不要把这条理由记录成 ADR，避免未来的架构审查再次提出同样建议？”只有未来探索者确实需要这条理由才能避免重复建议时才提出；跳过临时理由（“现在不值得”）和显而易见的理由。
- **想为深化模块探索不同接口？** 调用 Skill 工具加载 "codebase-design"，使用其中设计两次、并行比较子代理方案的模式。

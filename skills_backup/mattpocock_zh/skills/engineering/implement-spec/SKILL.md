你已获得一份规格说明。它应当关联了一组工单，描述如何实现该规格。

用户应已提供问题跟踪系统的信息。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

目标是在一个**集成分支**上实现整份规格，并按该问题跟踪系统的工作关闭方式解决每一张工单。

这些工单不是步骤清单，而是一张带有阻塞关系的**任务图**。因此，始终存在一组可以开始处理的工单，称为**可执行前沿**。

为每个子代理开启全新的上下文窗口。

与子代理之间的通信应保持精简。主要通过**上下文指针**传递信息，例如指向规格说明、工单、研究笔记和此前提交的引用。不要重复指针已经能够提供的信息。

尽可能让**实现子代理**在后台运行，以获得最大并发度。

## 步骤

1. 阅读规格说明和工单，理解任务图。

2. （可选）使用一个**探索子代理**完成工单所需的探索，例如阅读代码库中的相关文件或外部文档。确保它能够保存文件：应将 Markdown 笔记保存在仓库外、所有后续子代理均可访问的目录。这样，**实现子代理**就能专注于实现，而非探索。

3. 创建集成分支。如果问题跟踪系统通过 PR 关闭工作，或者用户要求创建 PR，就在步骤 5 第一次合并后开启草稿 PR，并标记其将关闭对应的规格和工单（相对 main 没有新增提交的分支无法开启 PR）。

4. 为每张工单使用一个全新的**实现子代理**，每个代理都在独立 worktree 和独立分支中工作。每个实现子代理都应：
   - 在开始前确认 worktree 基于集成分支；如果不是，就重置到该分支；
   - 调用 Skill 工具加载 `tdd` 来实现工单；
   - 在报告完成之前，将集成分支的最新提交合并到自己的分支。

5. **实现子代理**完成后，使用一个**合并子代理**将其工作合并到集成分支。

6. 如果这改变了可用工单的**可执行前沿**，就启动更多**实现子代理**处理新解锁的工单，以尽可能提高并发度。

7. 所有工单完成后，在集成分支上调用 Skill 工具加载 `code-review`。用一个全新的**实现子代理**统一修复代码审查提出的全部问题。

8. 如果已有草稿 PR，将其标记为可供审查。否则，按问题跟踪系统的工作关闭方式解决每张工单，并报告集成分支。

9. 清理所有**实现子代理**的 worktree。

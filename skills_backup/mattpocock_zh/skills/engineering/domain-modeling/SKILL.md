# 领域建模

在设计过程中主动构建并打磨项目的领域模型。这是一项*主动*实践：质疑术语、构造边界场景，并在术语和决策明确的当下将其记录下来。（仅仅为了了解词汇而*阅读* `GLOSSARY.md`，不属于此技能的范围；那只是任何技能都可以遵循的一条习惯。本技能用于改变模型，而不只是使用已有模型。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明仓库有多个上下文。该映射文件指出每个上下文的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 特定上下文的决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

按需创建文件：只有确实有内容要写时才创建。如果还没有 `GLOSSARY.md`，就在第一个术语确定时创建。如果还没有 `docs/adr/`，就在需要第一份 ADR 时创建。

## 会话过程中

### 对照术语表提出质疑

用户使用的术语与 `GLOSSARY.md` 中的现有定义冲突时，立即指出。例如：“你的术语表将‘取消’定义为 X，但你现在似乎指的是 Y。究竟是哪一种？”

### 澄清模糊语言

用户使用含糊或多义的术语时，提出精确的规范术语。例如：“你说的‘账户’，是指 Customer 还是 User？它们是不同的概念。”

### 讨论具体场景

讨论领域关系时，用具体场景进行压力测试。构造能够触及边界情况的场景，促使用户明确概念之间的边界。

### 与代码交叉核对

用户描述某项功能如何运作时，检查代码是否一致。发现矛盾就明确指出：“代码会取消整个 Order，但你刚才说可以部分取消。哪一种才是正确的？”

### 即时更新 GLOSSARY.md

术语一旦确定，立即更新 `GLOSSARY.md`，不要积攒后统一处理。采用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md) 中的格式。

`GLOSSARY.md` 应完全不包含实现细节。不要将它当作规格说明、草稿区或实现决策的存放处。它只是一份术语表。

### 谨慎提议编写 ADR

只有以下三个条件全部成立时，才提议创建 ADR：

1. **难以逆转**：将来改变主意需要付出显著成本。
2. **缺少上下文就难以理解**：未来的读者会疑惑“为什么当时这样做？”
3. **来自真实的权衡**：确实存在其他可行方案，并且有明确理由选择了当前方案。

缺少任何一项，就不写 ADR。采用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。

# 原型

原型是**用来回答问题的一次性代码**。要回答的问题决定原型的形态。

## 选择方向

根据用户提示、相关代码，或者在用户在线时直接询问，确定要回答哪一个问题：

- **“这个逻辑或状态模型是否合理？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的独立 HTML 文件，包含自由操作按钮和分标签的引导演示，推动状态机经历那些难以仅凭纸面推理的场景，并让非开发人员也能操作。
- **“它应该长什么样？”** → [UI.md](UI.md)。在同一路由上生成多种差异显著的 UI 方案，通过 URL 查询参数和底部悬浮栏切换。

这两个方向产生的产物截然不同，选错方向会浪费整个原型。如果问题确实含糊，且无法联系用户，就选择与相关代码更匹配的方向（后端模块对应逻辑，页面或组件对应 UI），并在原型顶部说明这一假设。

## 两个方向都适用的规则

1. **从第一天起就是一次性的，并明确标注。** 将原型代码放在接近实际使用位置的地方，例如被验证模块或页面的旁边，便于理解上下文；命名应让普通读者一眼看出它是原型，而非生产代码。一次性 UI 路由应遵守项目已有的路由约定，不要另创顶层结构。
2. **运行方式足够简单。** UI 原型只需项目任务运行器中的一条命令即可启动，例如 `pnpm <name>`、`python <path>`、`bun <path>`。逻辑演示则是用户双击即可打开的独立 HTML 文件。无论哪一种，启动都不应费心思考。
3. **默认不持久化。** 状态保存在内存中。持久化是原型要*检验*的内容，而不是它应依赖的条件。如果问题明确涉及数据库，就使用临时数据库或本地文件，并用清晰的“PROTOTYPE，可随时清空”命名。
4. **省去精雕细琢。** 不写测试，不做超出*可运行*所需的错误处理，不做抽象。目的在于快速获得认识。
5. **展示状态。** 每次操作后（逻辑原型）或每次切换方案时（UI 原型），打印或渲染全部相关状态，让用户看到发生了什么变化。
6. **完成后留存。** 将验证成立的决策融入正式代码，再把原型本身作为**一手资料**保存：提交到主分支之外的一次性分支，并在实现工单上留下指向该分支的上下文指针。也要在工单或提交中记录答案，即结论及其解决的问题。主分支只保留经过验证的决策。

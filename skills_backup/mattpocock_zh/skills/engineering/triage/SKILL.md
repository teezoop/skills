# 分诊

在项目问题跟踪系统中，通过一套小型分诊角色状态机推进工单。

如果仓库将外部 pull request 也视为请求入口（见问题跟踪系统配置），分诊同样覆盖它们：**PR 是附带代码的工单**，使用相同角色、状态和状态机，只有少量差异在下文以“对于 PR”注明。根据跟踪系统配置，将裸 `#42` 解析成 issue 或 PR。

分诊期间发布到问题跟踪系统的每条评论或每张工单，**必须**以下述免责声明开头：

```
> *这段内容由 AI 在分诊过程中生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写经得起时间的代理任务简报。
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作。

## 角色

两个**类别**角色：

- `bug`：某些功能损坏。
- `enhancement`：新功能或改进。

五个**状态**角色：

- `needs-triage`：需要维护者评估。
- `needs-info`：等待报告者补充信息。
- `ready-for-agent`：规格充分，已可交给无人值守代理。
- `ready-for-human`：需要人工实现。
- `wontfix`：不会采取行动。

对于 PR，应结合附带代码理解相同状态：`ready-for-agent` 表示已有任务简报，代理应对差异采取下一步行动；`ready-for-human` 表示已可由人类合并。

每张完成分诊的工单应恰好包含一个类别角色和一个状态角色。如果状态角色冲突，先标出冲突并询问维护者，再做其他事。

这些是规范角色名。问题跟踪系统中实际使用的标签字符串可能不同，用户应已提供映射。如果没有，请让用户运行 `/setup-matt-pocock-skills`。

状态迁移：未标记工单通常先进入 `needs-triage`，再进入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 返回 `needs-triage`。维护者可以随时覆盖状态；遇到看起来异常的迁移，应先指出并询问，再继续。

## 调用方式

维护者调用 `/triage`，并用自然语言描述意图。理解请求并行动，例如：

- “给我看看有什么需要我关注。”
- “看一下 #42。”（issue 或 PR）
- “把 #42 移到 ready-for-agent。”
- “有哪些工作已经可以交给代理？”

## 展示待关注事项

查询问题跟踪系统，分成三组展示，每组按最旧优先排序：

1. **未标记**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **上次分诊笔记后报告者有新活动的 `needs-info`**：需要重新评估。

如果 PR 在范围内，将外部 PR 也纳入这些组，并为每行标记 `[PR]` 或 `[issue]`。发现阶段只呈现*外部* PR（谁算外部由跟踪系统配置定义），协作者正在进行中的 PR 不算分诊工作。这个筛选只适用于发现阶段；用户明确点名的 PR 无论作者是谁，都要分诊。

展示每组数量，并为每项提供一句话摘要，让维护者选择。

## 分诊指定 issue 或 PR

1. **收集上下文。** 阅读完整 issue 或 PR，包括正文、评论、标签、作者和日期；对于 PR，还要读差异。解析之前的分诊笔记，避免重复询问已解决的问题。探索代码库时使用项目领域术语表，并遵守相关区域中的 ADR。对代码库执行两项检查：(a) **重复需求**：按领域概念搜索已有的请求行为实现，不要只按请求原词搜索，并报告查找过的位置。若找到，属于已经实现的 `wontfix`，转步骤 5。(b) **先前拒绝记录**：阅读 `.out-of-scope/*.md`，指出任何与当前请求相似的记录。

2. **给出建议。** 向维护者说明建议的类别、状态及理由，并简要总结与请求有关的代码库情况，包括是否已经实现。等待指示。

3. **验证主张。** 深入追问之前，先检查主张是否成立。对于缺陷，按报告者步骤复现；对于 PR，确认差异确实做到其声称的事情，检出后运行相关测试或命令。报告结果：已确认（附代码路径）、验证失败，或信息不足（这是应设为 `needs-info` 的强信号）。经过验证的任务简报会更可靠。

4. **深入追问（如需要）。** 如果请求还需充实，调用两次 Skill 工具，分别加载 "grilling" 和 "domain-modeling"，每轮一组问题，逐步打磨请求，澄清领域术语，并在决策确定时即时更新 `GLOSSARY.md` 和 ADR。

5. **应用结果：**
   - `ready-for-agent`：发布代理任务简报评论，见 [AGENT-BRIEF.md](AGENT-BRIEF.md)。
   - `ready-for-human`：结构与代理任务简报相同，但说明为什么不能交给代理，例如需要判断、外部访问、设计决策或人工测试。
   - `needs-info`：发布分诊笔记，模板见下文。
   - `wontfix`：关闭工单，评论内容取决于*原因*：
     - **已实现**：代码库中已有该变更，指出其位置；**不要**写入 `.out-of-scope/`，因为该知识库存放*被拒绝*的请求，而非已经构建的功能。
     - **拒绝缺陷请求**：礼貌说明理由后关闭。
     - **拒绝增强请求**：写入 `.out-of-scope/`，在评论中链接该记录，然后关闭，见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)。
   - `needs-triage`：应用该角色；如果有部分进展，可以选择发表评论。

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，信任其判断，直接应用角色。先确认将执行的操作，例如角色修改、评论或关闭，然后行动。跳过深入追问。如果未经追问就转到 `ready-for-agent`，询问是否需要编写代理任务简报。

## Needs-info 模板

```markdown
## 分诊笔记

**目前已确定的内容：**

- 要点 1
- 要点 2

**仍需要你（@reporter）提供的信息：**

- 问题 1
- 问题 2
```

将深入追问中所有已解决内容记录到“目前已确定的内容”，避免丢失成果。问题必须具体、可操作，不要只说“请提供更多信息”。

## 恢复此前会话

如果 issue 或 PR 已有分诊笔记，先阅读，检查报告者是否回答了未解决问题，呈现更新后的情况再继续。不要重复询问已解决的问题。

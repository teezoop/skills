# 测试驱动开发

TDD 是红灯 → 绿灯的循环。本技能是让该循环产出值得保留的测试的参考：什么是好测试、测试应放在哪里、有哪些反模式，以及循环中的规则。每一节都适用于每一轮循环，应在循环开始前及过程中查阅，而非结束后再看。

探索代码库时，阅读 `GLOSSARY.md`（如果存在），使测试命名和接口用语符合项目的领域语言，并遵守所修改区域中的 ADR。

## 什么是好测试

测试通过公开接口验证行为，而不是验证实现细节。代码可以完全改变，测试不应因此变化。好的测试读起来像规格说明：“用户可以用有效购物车结账”准确指出存在什么能力，而且不关心内部结构，因此能够经受重构。

示例见 [tests.md](tests.md)，模拟依赖的指导见 [mocking.md](mocking.md)。

## 接缝：测试应放在哪里

**接缝（seam）**是测试所针对的公开边界：你可以在这里观察行为，而不必探入内部。测试应位于接缝处，绝不针对内部细节。

**只在事先约定的接缝处编写测试。** 写任何测试前，先列出待测接缝并与用户确认。不得为未经确认的接缝编写测试。你不可能测试所有内容，提前约定接缝，才能把测试投入放在关键路径和复杂逻辑上，而不是覆盖每一种边界情况。

询问：“公开接口是什么？哪些接缝需要测试？”对每个建议的接缝，用一句话说明它能捕获什么、会遗漏什么。

如果接口本身的形态尚不明确，例如模块应有多深、接缝应在哪里、接口应暴露什么，就调用 Skill 工具加载 "codebase-design"，查阅术语。它是模块、接口、深度、接缝、适配器、投入收益和局部性等术语的共同来源，是供查阅的参考，而不是要执行的一场会话。

## 反模式

- **与实现耦合**：模拟内部协作者、测试私有方法，或通过旁路验证行为（例如查询数据库，而非使用接口）。典型迹象是：行为没有变化，但重构却让测试失败。
- **同义反复**：断言用与代码相同的方式重新计算期望值，例如 `expect(add(a, b)).toBe(a + b)`、用相同推导方式手工构造快照，或断言某个常量等于它自身。这类测试在构造上必然通过，不可能与代码产生分歧。期望值必须来自独立的真实依据，例如已知正确的字面值、完整算例或规格说明。
- **水平切片**：先写完所有测试，再写所有实现。批量测试验证的是*想象中的*行为：你测试的是事物的*形态*，而非用户可见的行为，导致测试对真实变化不敏感，并在理解实现之前就锁定了测试结构。应改用**垂直切片**：一个测试 → 一次实现 → 重复。每个测试都像一发**曳光弹**，根据上一轮学到的内容调整方向。

## 循环规则

- **先红灯，后绿灯。** 先写会失败的测试，再仅编写足以使其通过的代码。不要预判未来测试，也不要加入推测性的功能。
- **一次只做一个切片。** 每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于这个循环。** 重构属于审查阶段（见 `code-review` 技能），而不是红灯 → 绿灯的实现循环。
